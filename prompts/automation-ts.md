## 快速摘要

**最重要的事情**：功能正確是底線，但這是一份**作品集（portfolio）**，要展示給工程團隊看——因此在正確的前提下，採用**乾淨、慣例化、可維護**的結構。

- 用 Next.js 慣例化的結構，正確實作所有規則（依 Feature Files 中的 Rule 數量）
- 業務規則（如拆帳 / 債務化簡）的**計算過程**要清楚呈現給使用者——這對拆帳類產品本身就是有價值的 UX，不只是 demo
- 測試資料（seed）要充足，足以觸發各種規則場景

> 部署與實際驗證屬於獨立階段，見 `prompts/deploy.md`。

**要做的**：

- 實作 `spec/features/` 中定義的所有功能

**不要做的**：

- 不要為了展示而過度設計（不需要硬套 DDD / Clean Architecture / 多餘的抽象層）
- 不要做得草率到無法維護——慣例化的清晰結構是底線
- 不要實作規格中未提及的功能，不要腦補規格沒提到的內容

## 核心原則

### 1. 功能正確性是底線

**功能正確性是不可妥協的底線；在正確的前提下，追求乾淨可維護的結構。**

- **每一條規則都必須 100% 正確實作**
- 優先確保業務邏輯完全符合規格
- 採用 Next.js / React 的**慣例化結構**：合理的資料夾分層、清楚的命名、單一職責的函式
- **避免過度設計**：不為了展示而硬套 Repository Pattern、DDD、Clean Architecture 等——但也不能草率到難以維護。目標是「資深工程師讀起來覺得乾淨、合理、好懂」

### 2. 絕對忠於規格原則

**嚴格遵守 `spec/` 資料夾中的所有規格內容，禁止任何腦補、假設或擴充。**

- 只實作 `spec/erm.dbml` 中定義的資料實體與屬性
- 只實作 `spec/features/*.feature` 中定義的功能與規則
- ERM 或 Feature Files 中沒有寫的內容，**絕對不准出現在程式碼中**
- 不添加「可能需要的欄位」「預留功能」「合理的優化」
- 不實作規格中未提及的驗證、邏輯或 UI 元素

### 3. 規則可追溯性原則

- 在實作業務邏輯的程式碼中（無論是 Service、Server Action、Route Handler 或其他地方），**必須將每條規則以註解形式逐條抄寫**
- 每個規則對應的實作邏輯必須清晰標註，確保規格與程式碼的 1:1 對應關係
- 這是這份作品集的賣點之一：任何人都能從程式碼回溯到規格條目

### 4. 資料模型嚴格對應原則

- `prisma/schema.prisma` 必須完整對應 `spec/erm.dbml`
- 所有 ERM 中的約束條件（note 中的限制）都必須在資料層強制執行：
  - 能用 Prisma schema 表達的（型別、`@unique`、關聯、`@default`、非空）→ 用 Prisma 表達
  - Prisma 無法表達的（數值範圍、跨欄位 CHECK）→ 用 migration 中的原生 SQL `CHECK` constraint 補上
  - 規格定義的存取規則 → 用 Supabase **RLS Policies** 落實
- 屬性的資料型別、唯一性、外鍵關係都必須在資料庫層面強制執行

### 5. 前端完整展示原則（重點，且為產品價值）

**前端是展示功能正確性的關鍵；對拆帳類產品而言，展示「計算過程」本身就是核心 UX。**

- 前端 UI 必須能夠**完整展示** `spec/features/*.feature` 中的所有 Examples
- 每個 Rule 的驗證結果都要清楚顯示
- 使用者應能透過網頁操作，重現 Feature File 中的任一 Example 場景
- 關鍵資訊必須清楚顯示（依規格內容調整，以下為常見範例）：
  - 主要實體的屬性資訊（依 ERM 定義）
  - 業務規則的計算過程（中間步驟、條件判斷）——例如拆帳：原始各筆欠款 → 化簡步驟 → 最終轉帳清單
  - 計算結果的展示（原始值、調整後的值）
  - 狀態資訊（若規格有定義狀態轉換）

> 部署與自動化驗收原則見 `prompts/deploy.md`。

## 執行步驟

### 階段 1：深度理解規格

#### 1.1 研讀資料模型

- 讀取 `spec/erm.dbml`
- 識別所有實體 (Table)、屬性 (Column)、關係 (Relationship)
- 記錄每個屬性的定義、資料型別、限制條件
- 記錄所有跨屬性不變條件

#### 1.2 研讀功能模型

- 讀取 `spec/features/` 下所有 `.feature` 檔案
- 識別每個 Feature 及其涵蓋的所有 Rule
- 研讀每個 Rule 的所有 Example（Given-When-Then）
- **特別注意**：
  - 前置條件（Pre-condition）：功能執行前的驗證規則
  - 後置條件（Post-condition）：功能執行後的系統狀態變更

#### 1.3 研讀設計與 UI 規範

- 讀取 `spec.md` 中「設計與 UI 規範」一節（呈現與互動需求，不在 ERM／Gherkin 中，需由本階段直接落實）
- 對照該節提到的 `doc/design-refs/*.jpg` 截圖，記錄每張截圖對應的頁面／區塊，以及截圖中出現的欄位、互動方式、佈局重點
- 截圖中被紅線劃掉之處代表不需實作，需明確排除
- 視覺風格與顏色以整體一致為原則，優先使用 shadcn/ui 既有元件，不足時才客製化

#### 1.4 建立規格檢查清單

在開始開發前，建立內部檢查清單：

- [ ] 已識別所有實體與屬性
- [ ] 已識別所有實體關係
- [ ] 已識別所有功能與規則
- [ ] 已理解每個規則的所有 Example
- [ ] 已記錄所有約束條件
- [ ] 已對照 `doc/design-refs/*.jpg` 記錄每個頁面的欄位、互動方式與佈局重點
- [ ] 已確認無任何規格遺漏或歧義

### 階段 2：資料庫設計與實作（Prisma + Supabase）

#### 2.1 產生 Prisma Schema

- 依據 `spec/erm.dbml` 撰寫 `prisma/schema.prisma`
- 每個 Table 對應一個 Prisma model
- 資料型別對應如下：
  - `int` → `Int`
  - `long` → `BigInt`
  - `float` → `Decimal`（金額類務必用 `Decimal`，避免浮點誤差）
  - `bool` → `Boolean`
  - `string` → `String`
- 關係使用 Prisma 的關聯語法（`@relation`），對應 ERM 中的 ref

#### 2.2 實作約束條件

對於 ERM 中每個屬性的 note 所描述的限制條件：

- 唯一性限制 → Prisma `@unique`
- 非空限制 → Prisma 非 nullable 欄位
- 外鍵關聯 → Prisma `@relation`
- 數值範圍限制（如 `>= 0`） → migration 中以原生 SQL `CHECK` constraint 補上
- 跨屬性不變條件（涉及多欄位） → migration 中以原生 SQL `CHECK` constraint 補上
- 規格定義的存取規則 → Supabase **RLS Policies**（僅在規格定義了身分 / 權限時）

#### 2.3 建立測試資料（Seed Data）【重要】

**必須建立豐富的測試資料，讓使用者能立即操作驗證功能**

於 `prisma/seed.ts` 撰寫 seed script，建立原則：

1. **識別核心實體**：根據 `spec/erm.dbml` 識別系統的核心實體
2. **建立基礎資料**：為每個核心實體建立至少 5-10 筆測試資料
3. **涵蓋測試場景**：測試資料要能觸發 Feature Files 中的各種 Rules

測試資料設計要能觸發各種規則：

- 邊界條件（例如：金額剛好達標 / 差一點）
- 業務規則（例如：拆帳分攤、債務化簡、各種優惠或分帳模式）
- 錯誤情境（例如：違反前置條件的資料）

#### 2.4 套用 Migration 與 Seed

- 使用 `prisma migrate dev`（本機）/ `prisma migrate deploy`（線上）建立資料表與約束
- 使用 `prisma db seed` 載入測試資料
- 確保流程可重複執行

### 階段 3：後端開發

**重點：正確實作所有規則，使用指定的技術棧，結構慣例化、清楚易讀**

#### 3.1 實作策略

- 使用 Next.js Route Handlers / Server Actions
- 將業務邏輯（特別是拆帳 / 化簡演算法）抽成獨立、可測試的純函式或 service 模組
- **關鍵是：每條規則都要正確實作，邏輯清楚易讀，並可追溯回規格**

#### 3.2 API / Action 設計

根據 `spec/features/` 中的 Feature Files，為每個主要操作建立對應的端點（Route Handler 或 Server Action）。

**設計原則**：

1. 為每個 Feature 建立至少一個主要端點
2. 查詢類操作使用 GET / RSC 讀取，變更類操作使用 POST/PUT/DELETE 或 Server Action
3. 回傳適當的狀態碼與錯誤訊息
4. 端點命名清楚反映功能

#### 3.3 規則實作與註解（核心重點）

**必須將每條規則以註解形式逐條抄寫，並確保實作正確**

**註解格式要求**：

```
/**
 * Feature: [Feature 名稱]
 * Rule: [Rule 描述]
 * 對應規格：spec/features/[檔案名稱].feature
 */
```

**所有規則必須逐條實作**：

- 識別 `spec/features/` 中所有 `.feature` 檔案的 Rules
- 每條 Rule 都要有對應的註解與實作
- 特別注意複雜規則：多步驟計算、條件分支、多重規則疊加順序

#### 3.4 資料存取

- 使用 Prisma Client 存取資料庫
- 透過環境變數設定 `DATABASE_URL`
- 涉及金額計算一律使用 `Decimal`，避免浮點誤差

### 階段 4：前端開發【關鍵階段】

**核心目標：讓使用者透過網頁操作，親眼驗證所有規則都被正確實作；對拆帳產品而言，清楚呈現計算過程即為核心體驗**

#### 4.1 實作策略

- 使用 Next.js App Router（RSC 優先，互動處用 Client Component）
- UI 以 shadcn/ui + Tailwind 構成；伺服器狀態用 TanStack Query 管理
- 樣式不需華麗，但資訊必須清楚易讀、結構乾淨
- **頁面與元件必須依 `spec.md`「設計與 UI 規範」與對應的 `doc/design-refs/*.jpg` 實作**：欄位、佈局、互動方式（如彈窗、Tab、Toast 文案、三個點點選單等）以截圖與該節文字為準；截圖中被紅線劃掉的內容不要做

#### 4.2 頁面規劃

根據 `spec/features/` 中的 Feature Files，並對照 `spec.md`「設計與 UI 規範」一節，規劃前端頁面結構。

1. 每個主要 Feature 至少有一個對應的操作介面
2. 頁面之間的導航流程符合使用者操作順序與該節描述（如：進入旅程後的 Tab 順序、加入旅程的 Toast 提示等）
3. 關鍵操作結果（如拆帳結果）要有專門的展示頁面，佈局對照對應截圖

#### 4.3 前端必須完整展示的資訊（非常重要）

在結果展示頁面，必須清楚顯示：

1. **主要資料明細**：根據規格顯示核心資料
2. **計算前的原始值**：明確標示計算前的基礎數值
3. **業務規則計算過程**（重點）：
   - 每一條被觸發的規則都要列出
   - 顯示規則的判斷條件與結果、對數值的影響
   - 多重規則疊加時，顯示套用順序
   - （拆帳範例）原始各筆欠款明細 → 化簡演算法的中間步驟 → 最終最少筆數的轉帳清單
4. **最終計算結果**：明確標示最終數值
5. **狀態資訊**（若規格有定義）

#### 4.4 測試場景建議

前端應讓使用者能輕易重現 Feature Files 中的各種場景：基本流程、各業務規則觸發情境、多重規則疊加、邊界條件、錯誤情境。

## 行為規則

### 開發階段規則

1. **功能正確性是底線**：每條規則都要 100% 正確實作；在正確前提下追求乾淨可維護的結構
2. **嚴格遵守規格**：任何實作都必須有明確的規格依據，禁止腦補
3. **規則可追溯**：每個規則實作都要加註解，能追溯到具體的規格條目
4. **前端展示完整**：使用者要能透過前端畫面驗證所有規則，業務規則計算過程必須清楚展示
5. **測試資料豐富**：seed data 要包含足夠的測試資料，讓人能輕易測試各種場景
6. **約束強制**：資料約束優先在資料庫層面（Prisma / SQL CHECK / RLS）實作

> 驗收階段規則見 `prompts/deploy.md`。

### 溝通規則

1. **階段性報告**：每完成一個階段都要報告進度
2. **問題回報**：發現規格歧義或遺漏時立即回報
3. **不自行決定**：遇到規格未涵蓋的情況，詢問使用者而非自行決定

### 禁止事項

1. 不要為了展示而過度設計（不硬套 Repository Pattern、DDD、多餘抽象層）；但也不要草率到難以維護
2. 不要實作規格中沒有提到的功能
3. 不要添加「可能需要」的欄位或功能
4. 不要只顯示最終結果而不顯示業務規則計算過程

## 與其他 Prompt 的關係

- **前置階段**：`discovery.md`、`clarify-and-translation.md`、`formulation.md` 已產出完整規格
- **本階段角色**：自動化開發階段，將完整規格轉換為結構乾淨、規則正確的可運行應用程式
- **後續階段**：`deploy.md`——功能開發完成、使用者準備部署時執行，負責部署與自動化驗收
- **與 `prompts/tests/01`→`05`（四段式 TDD + 串接）的關係**：兩者是**同一個實作階段的替代路徑，不是接續關係**。若某個 feature 已經走過 `prompts/tests/` 的流程（有測試保護的業務邏輯模組 + 已串接的頁面），**不要**再對該 feature 跑本 prompt，本 prompt 會從規格重新推導一份自己的實作，可能與已測試的模組重複或衝突。本 prompt 僅適合完全沒走 TDD 流程、想一次做完的 feature。

## 注意事項

### 最重要的三件事

1. **功能必須正確**：每條規則都要 100% 正確實作，尤其是拆帳 / 化簡這類複雜業務邏輯
2. **前端必須展示計算過程**：使用者要能看到業務規則如何運作，這對拆帳產品本身就是核心 UX
3. **結構必須乾淨可維護**：這是作品集，工程師會讀你的程式碼——慣例化、清楚，但不過度設計

### 開發注意事項

1. **架構恰到好處**：用 Next.js 慣例的清晰結構，把業務邏輯抽成可測試模組；不為展示而過度抽象
2. **絕對不要腦補**：規格沒有提到的欄位、功能或規則，就不要實作
3. **金額用 Decimal**：避免浮點誤差
4. **遇到歧義立即停止**：發現規格有歧義或遺漏時，回報使用者而非自行決定

> 部署注意事項見 `prompts/deploy.md`。
