## 釐清策略說明

- 本輪掃描範圍:`spec/features/查看結算.feature`,交叉比對 `spec/erm.dbml`(expenses、expense_splits、trip_members)與 `新增開支.feature`(尾差分配、精度慣例)、CLAUDE.md 之 MVP 範圍與技術選型
- 已檢查 `.clarify/resolved/`:均分尾差之加入順序依據、分攤金額可為 0、付款人可不參與分攤、「結算為即時計算、無已結清狀態」等既有決議不重複提問
- 本輪 7 個釐清項目皆已解決並歸檔:
  1. 套用結清清單定位 → 僅為驗證性規則(演算法不變條件,無使用者操作、無持久化),Rule 4 改寫為由開支推導、When 回到查看結算;ERM 不新增實體
  2. 演算法定義 → greedy 即可(最大債權配最大債務,至多 N−1 筆),Rule 措辭由「最少轉帳筆數」改為可驗證的演算法定義
  3. 輸出決定性 → 淨額相同時依團員加入旅程的先後順序優先配對(沿用均分尾差慣例),清單依轉帳產生順序排列,新增 Rule 與同額欠款 Example
  4. 查看權限 → 非成員操作失敗,補上全案一致的「使用者必須是旅程成員」前置 Rule 與 Example
  5. 空狀態 → 無開支與淨額全歸零統一輸出空結清清單,新增 Rule 與兩個邊界 Example;UI「無需結算」文案屬設計規範層
  6. 零淨額團員 → 餘額清單列出所有團員含淨額 0 者(以 trip_members 為基底),新增 Rule 與未參與者 Example
  7. 即時性 → 需即時,沿用 TanStack Query × Supabase Realtime 整合(監聽 expenses 變更後 invalidate 重算),新增即時反映 Rule 與 Example;此決議將分帳頁納入即時同步範圍(原 MVP 清單字面僅行程)
