# 釐清問題

拖曳行程改變順序後，原本掛在該行程之後的交通時間（`transports.after_activity_id`）應該跟著該行程移動到新位置，還是留在原本的「順序位置」（改掛到現在排在該位置的另一個行程之後）？

# 定位

ERM：`transports.after_activity_id`（`spec/erm.dbml` 第 78 行），為 unique 外鍵，指向特定的 `activities.id`；語意是「接在某個具體行程之後」，而非「接在某個順序位置之後」。
Feature：`調整行程順序.feature` 目前的 Rule「成員拖曳後行程順序更新」與其 Example，只驗證 `order` 欄位的變化，完全未提及交通時間；`行程時間軸.feature` 的時間軸計算會讀取「行程之後的交通時間」，若交通時間的歸屬在拖曳後與直覺不符，時間軸計算結果會跟著錯誤。

具體情境：日期內有 道頓堀(order1，之後接交通15分) → 心齋橋(order2)。使用者將 心齋橋 拖曳至 order1（道頓堀 變成 order2）。此時「15分交通時間」該如何處理？

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 交通時間跟著行程本體移動：`after_activity_id` 不變（仍指向道頓堀），因此拖曳後交通時間變成接在「新順序中排最後的道頓堀」之後 |
| B | 交通時間留在原本的順序位置：拖曳後改掛到「現在排在 order1 的行程」（即心齋橋）之後，`after_activity_id` 需隨拖曳更新 |
| C | 拖曳有交通時間的行程時操作直接失敗，需使用者先手動刪除交通時間才能調整順序 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

- `spec/erm.dbml`：`transports` 的 Note 需補充拖曳重排時 `after_activity_id` 的處理規則（跨屬性不變條件）
- `spec/features/調整行程順序.feature`：需新增「拖曳有交通時間的行程」對應 Rule 與 Example
- `spec/features/行程時間軸.feature`：需確認拖曳後時間軸計算是否仍正確反映交通時間的新歸屬

# 優先級

High
- 屬於資料模型的核心決策，直接影響 `transports` 表的更新邏輯與時間軸計算正確性；若不釐清，實作時容易產生交通時間「跟錯行程」的邏輯錯誤。

---
# 解決記錄

- **回答**：B - 交通時間留在原本的順序位置：拖曳後改掛到「現在排在該順序位置的行程」之後，`after_activity_id` 需隨拖曳更新
- **更新的規格檔**：`spec/erm.dbml`、`spec/features/調整行程順序.feature`
- **變更內容**：在 `transports` Table Note 中新增跨屬性不變條件（拖曳調整順序時，交通時間依附於原本的順序位置，系統需將 `after_activity_id` 重新指向調整後排在該順序位置的行程）；在 `調整行程順序.feature` 新增「交通時間依附於順序位置，不隨行程本體移動」規則與對應 Example
