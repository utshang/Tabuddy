# 釐清問題

編輯旅程將起迄日範圍縮小，導致部分既有旅程日期（days）落在新範圍之外時，這些日期底下的行程（activities）與交通時間（transports）應如何處理？

# 定位

ERM：`days`（依旅程起迄日自動產生，`days.trip_id > trips.id`）與 `activities`（`activities.day_id > days.id`）、`transports`（依附 `activities`）。目前 `trips` 的 Note 僅定義「end_date >= start_date」，未定義編輯後範圍縮小時對子實體 `days` / `activities` / `transports` 的處理規則。
Feature：編輯旅程 — 目前僅有「將名稱改為」的 Example，完全未涵蓋編輯起迄日的情境，因此此邊界情況尚無任何 Rule 或 Example。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 若新範圍外的旅程日期底下已有行程（activities），操作直接失敗並提示衝突，使用者需先清空才能縮減 |
| B | 允許編輯，新範圍外的旅程日期連同其下所有行程與交通時間一併刪除（cascade delete） |
| C | 允許編輯，新範圍外的旅程日期與行程資料保留不刪除，僅日期本身不再顯示於旅程範圍內 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

- `spec/erm.dbml`：`trips` / `days` 的跨屬性不變條件與 cascade 規則需補充說明
- `spec/features/編輯旅程.feature`：需新增 Rule + Example（縮減起迄日且範圍外有行程時的行為）
- 行程時間軸、新增/刪除行程等 feature 的資料一致性

# 優先級

High
- High：直接影響核心資料完整性與是否可能造成使用者資料遺失，且為編輯起迄日功能能否實作的前提決策

---
# 解決記錄

- **回答**：B（延伸） - 允許編輯，新範圍外的旅程日期連同其下所有行程與交通時間一併刪除，但若範圍外已有行程，刪除前須提醒使用者確認；若範圍外無行程則直接刪除不需確認
- **更新的規格檔**：`spec/features/編輯旅程.feature`、`spec/erm.dbml`
- **變更內容**：
  - `編輯旅程.feature` 新增 Rule「縮減起迄日範圍且範圍外的旅程日期無行程時，系統直接刪除該範圍外的旅程日期」及對應 Example
  - 新增 Rule「縮減起迄日範圍且範圍外的旅程日期包含行程時，系統須經使用者確認才會刪除」，含「確認後刪除」與「取消確認不執行編輯」兩個 Example
  - `erm.dbml` 的 `days` Note 補充 cascade 刪除規則與確認機制說明
