# 釐清問題

交通工具（mode）欄位是否僅限 walking / driving / flight / transit 四個固定值？輸入其他字串時應如何處理？

# 定位

Feature：新增交通時間，Rule「交通工具為必填」（目前 Example 僅涵蓋空字串失敗案例，未涵蓋非法枚舉值）
ERM：`transports.mode` 型別為 string，note 列出四個建議值，但未強制為 enum 型別

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 僅接受四個固定值，前端以下拉選單限制，後端亦驗證，非法值操作失敗（建議搭配資料庫 enum 型別） |
| B | 僅前端下拉選單限制，後端不做嚴格驗證，信任前端輸入 |
| C | 允許任意自訂字串，四個值僅為建議選項，不做枚舉限制 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

影響 `新增交通時間.feature` 是否需新增「交通工具非固定值時操作失敗」的 Rule 與 Example；若決議為 A，需同步更新 `spec/erm.dbml` 將 `transports.mode` 定義為 enum 型別（Prisma schema 設計上的直接影響）；亦影響 `編輯交通時間.feature` 中「編輯後的交通工具為必填」規則的一致驗證邏輯。

# 優先級

Medium
- 影響資料庫欄位型別設計（string vs enum）與驗證層級，但不阻礙基本新增流程的核心實作。

# 解決記錄

- **回答**：C - 允許任意自訂字串，四個值僅為建議選項，不做枚舉限制
- **更新的規格檔**：spec/erm.dbml
- **變更內容**：`transports.mode` note 更新為「必填自由文字；UI 提供四個預設選項，但欄位本身不強制限制為此四個值」；`新增交通時間.feature` 既有的「交通工具為必填」規則已足夠涵蓋此決議（僅驗證非空，不驗證枚舉），無需新增規則

# 補充修訂（2026-07-13）

- **補充內容**：前端改為下拉選單呈現（不再是純自由輸入框），預設選項由四個改為五個「走路 / 開車 / 飛機 / 公車 / 火車」，並允許使用者透過下拉選單新增自訂名稱選項；後端驗證邏輯不變（仍不強制枚舉，`mode` 型別維持 string）
