# 釐清問題

當某行程之後已存在一筆交通時間時，使用者再次對該行程執行「新增交通時間」，系統應如何處理？

# 定位

Feature：新增交通時間（整體功能邊界，未有對應 Rule）
ERM：`transports.after_activity_id` [unique, not null]，note 明確指出「每個行程後最多一段交通時間」

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 操作失敗，提示使用者該行程已有交通時間，須改用「編輯交通時間」 |
| B | 視為隱含編輯，直接覆蓋既有交通時間的內容 |
| C | 前端在偵測到已有交通時間時，直接不顯示「新增」入口（僅顯示「編輯」），後端仍以失敗防呆 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

影響 `新增交通時間.feature` 是否需新增一條 Rule 與對應 Example；影響後端新增交通時間 API 的驗證邏輯（是否需先查詢 `after_activity_id` 是否已存在）；影響前端「新增」按鈕在已有交通時間時的顯示邏輯；與 `編輯交通時間.feature` 的功能邊界劃分有直接關聯。

# 優先級

High
- 直接對應 ERM 中 `after_activity_id` 的 unique 約束，若不釐清，新增交通時間的核心驗證邏輯無法實作完整。

---
# 解決記錄

- **回答**：C - 前端在偵測到已有交通時間時，直接不顯示「新增」入口（僅顯示「編輯」），後端仍以失敗防呆
- **更新的規格檔**：spec/features/新增交通時間.feature
- **變更內容**：新增 Rule「行程已有交通時間時新增操作失敗」與對應 Example，驗證後端在該情境下拒絕操作（前端入口顯示邏輯屬 UI 層行為，不納入此 Feature 規格）
