# 釐清問題

當旅程存在尚未結清（結算）的開支分帳時，owner 是否仍可刪除該旅程？

# 定位

Feature：`刪除旅程` 的「只有建立者可以刪除旅程」規則，目前僅涵蓋角色權限判斷，未涵蓋旅程帳務狀態（是否有未結清開支）對刪除操作的影響。與 `查看結算.feature`、`新增開支.feature` 有跨功能關聯。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 不限制：無論是否有未結清開支，owner 皆可直接刪除旅程（開支資料一併刪除）|
| B | 需額外警示：刪除時提示「尚有未結清帳務」，但仍允許刪除 |
| C | 禁止刪除：旅程有未結清開支時，刪除操作失敗，需先結清或清空開支 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

影響 `刪除旅程.feature` 是否需新增涉及 `expenses`/`expense_splits` 狀態的 Rule 與 Example，並與 [[trips_刪除旅程時關聯的旅程日期行程開支與成員記錄應如何處理]] 的答案互相依賴（若選擇連動刪除開支，則此題傾向選 A 或 B）。

# 優先級

Medium
- 原因：屬於邊界條件與跨功能規則的完整性問題，不阻礙核心刪除功能之架構設計，但影響資料一致性與測試涵蓋度。

---
# 解決記錄

- **回答**：B - 需額外警示：刪除時提示「尚有未結清帳務」，但仍允許刪除
- **更新的規格檔**：無新增 Rule/Example（說明如下）
- **變更內容**：
  - 確認 `spec/erm.dbml` 與 `spec/features/查看結算.feature` 中並無「已結清 / 未結清」的持久化狀態欄位（結算淨額為即時計算值，非儲存欄位），因此「未結清開支」並非可直接斷言的資料狀態，若強行加入 Given/Then 會違反無腦補原則
  - B 選項在「是否允許刪除」這個業務規則層面與 A 選項結果相同（皆允許刪除），差異僅在於刪除當下是否額外顯示警示文案；警示文案內容規格未明確定義，且屬於前端互動細節（非資料層斷言），依專案「Feature 檔案只放可驗證的資料規則」慣例不寫入 Gherkin
  - 「owner 可刪除含有開支的旅程」此一結果已由既有 Rule「刪除旅程後關聯的旅程日期、行程、交通時間、開支與成員記錄一併刪除」及其 Example（Given 旅程有開支 "門票"）涵蓋，故不重複新增 Rule
