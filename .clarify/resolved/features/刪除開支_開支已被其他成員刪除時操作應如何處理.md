# 釐清問題

使用者執行刪除（或在確認對話框按下確認）時，該開支已被其他成員先行刪除，操作應如何處理？

# 定位

Feature：`刪除開支` 全部四條 Rule 的 Given 皆假設開支存在，未涵蓋「開支已不存在」的異常情況。本專案主打多人即時協作（MVP 功能 3：行程與帳本在團員間即時同步），兩位成員同時開啟帳本、其中一人先刪除，另一人的畫面在同步事件抵達前仍顯示該開支，此時序邊界必然發生。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 視為成功（冪等）：目標狀態「開支不存在」已達成，不顯示錯誤，畫面同步移除 |
| B | 操作失敗：提示開支已被刪除，畫面同步移除該開支 |
| C | 不寫入規格：交由實作層（DB delete 影響 0 列即無事發生）自然處理 |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

影響 `刪除開支.feature` 是否新增時序邊界 Rule 與 Example；影響前端 mutation 的錯誤處理與 TanStack Query × Supabase Realtime 整合時的快取失效行為。同樣的時序議題也存在於刪除行程、刪除交通時間、刪除旅程（可組合釐清、統一慣例後回補各 feature）。

# 優先級

Medium
- 原因：不阻礙核心規則定義，但即時協作是本專案兩大主打功能之一，此邊界未定義會留下 UX 與錯誤處理的分歧空間。

---
# 解決記錄

- **回答**：A - 視為成功（冪等）：目標狀態「開支不存在」已達成，不顯示錯誤，畫面同步移除
- **更新的規格檔**：spec/features/刪除開支.feature
- **變更內容**：
  - 新增 Rule「開支已被其他成員先行刪除時，刪除操作視為成功（冪等）」
  - 新增 Example「確認刪除時開支已被其他成員刪除仍視為成功」，引入 Then 步驟「操作成功」（既有「操作失敗」的對稱句型）
  - 此決議可作為全案刪除類功能的通用慣例（刪除行程／交通時間／旅程可於後續 discovery 回補）
