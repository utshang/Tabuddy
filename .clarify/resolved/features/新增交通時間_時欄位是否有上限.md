# 釐清問題

交通時間的「時」（hours）欄位除了下界 >= 0 之外，是否需要上限？

# 定位

Feature：新增交通時間，Rule「時為必填且 >= 0」（目前標記 #TODO，尚無 Example）
ERM：`transports.hours` note 僅載明「>= 0」，未定義上界

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 無上限，僅需為非負整數；負值或非整數輸入時操作失敗 |
| B | 上限為 23（比照一天以內的交通時間） |
| C | 上限為 99（防呆用途，容許長途跨洲交通如飛行轉機） |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

影響 `新增交通時間.feature` 中「時為必填且 >= 0」規則的 Example 設計（是否需要上界失敗案例）；若決議有上限，需同步更新 `spec/erm.dbml` 中 `transports.hours` 的 note；亦影響 `編輯交通時間.feature` 中對應規則「編輯後的時必須 >= 0」的一致性。

# 優先級

Medium
- 屬於邊界條件而非核心流程，但答案會直接決定驗證邏輯與測試案例是否需要涵蓋上界情境。

---
# 解決記錄

- **回答**：C - 上限為 99（防呆用途，容許長途跨洲交通如飛行轉機）
- **更新的規格檔**：spec/erm.dbml, spec/features/新增交通時間.feature
- **變更內容**：`transports.hours` note 更新為「>= 0 且 <= 99」；Feature 中 Rule 更名為「時為必填且 >= 0 且 <= 99」並新增 Example 驗證超過上限時操作失敗

# 修訂記錄（2026-07-13）

- **修訂後回答**：A - 無上限，僅需為非負整數；負值或非整數輸入時操作失敗
- **更新的規格檔**：spec/erm.dbml, spec/features/新增交通時間.feature
- **變更內容**：`transports.hours` note 改回「必須為 >= 0 的整數，無上限」；Feature 中 Rule 改回「時為必填且 >= 0」，並將原本「時超過上限時操作失敗」的 Example 換成「時為負數時操作失敗」（時 -1）
