# 釐清問題

分享連結（invite_token）是否為旅程建立後永久固定不變，或是否需要提供「重新產生」／「撤銷」機制？

# 定位

ERM：`trips.invite_token` 標記為 `unique, not null`，由 `建立旅程.feature`「建立後系統同時產生該旅程唯一的 invite_token」規則於建立時產生一次；`erm.dbml` 未定義任何後續變更 invite_token 的規則。
Feature：`分享旅程.feature` 目前僅涵蓋「取得現有分享連結」，未涵蓋連結外流後的因應措施；`加入旅程.feature` 也僅處理「無效 token」與「已加入」情境，未處理「連結已被撤銷/過期」情境。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | invite_token 永久固定，不提供重新產生或撤銷機制（MVP 不處理連結外流風險） |
| B | 提供「重新產生分享連結」功能，owner 可讓舊連結失效並產生新 token，應新增對應 Rule + Example |
| C | 提供連結有效期限機制（例如 N 天後失效） |
| Short | 提供其他簡短答案（<=5 字）|

# 影響範圍

- `spec/features/分享旅程.feature`：是否新增「重新產生分享連結」Rule
- `spec/erm.dbml`：`trips.invite_token` 的可變性與相關規則
- `spec/features/加入旅程.feature`：若連結可失效，需新增「連結已撤銷/過期」的操作失敗 Example

# 優先級

Low
- Low：不阻礙 MVP 核心分享流程，屬安全性/完整性強化選項；依 CLAUDE.md 範圍紀律屬於應「先問再做」的延伸功能，非必要不擴大範圍

# 解決記錄

- **回答**：A - 分享連結永久固定，不提供重新產生或撤銷的功能（MVP 先不處理連結外流的風險）
- **更新的規格檔**：`spec/erm.dbml`
- **變更內容**：`trips.invite_token` 的 note 補充「建立後永久固定，不提供重新產生或撤銷機制」，明確排除該延伸功能於本輪範圍外
